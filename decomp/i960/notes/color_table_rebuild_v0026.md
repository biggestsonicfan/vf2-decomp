# Color table rebuild algorithm (v0.0.26)

`0x00002c38..0x00002de0` is now fully reconstructed from the VF2 2.1 i960 ROM. This is the routine called by `display_color_profile_apply` after it copies the three profile scale bytes to `0x005000e0..0x005000e2`.

The routine is substantially larger than the current selector-3 synthetic poststate suggests: the two final flag writes are only its epilogue. Its primary architectural side effect is an 8,064-byte generated color table rooted at `0x00546008`.

## Table layout

The destination is divided into 28 pages of `0x120` bytes each:

```text
page 0: 0x00546008 + 0x0000
page 1: 0x00546008 + 0x0120
...
page 27: 0x00546008 + 0x1e60
end:    0x00546008 + 0x1f80
```

Page 0 is cleared completely with eighteen `stq` stores.

Each generated page contains 48 RGB triples. A triple is three little-endian 16-bit channel values, therefore:

```text
48 * 3 * 2 = 288 bytes = 0x120
```

The first triple of every generated page is explicitly zeroed. The remaining 47 triples are generated by the inner loop.

## Inputs

The six source bytes form three `(base, span)` pairs:

```text
red:   base = u8[0x00500234], span = u8[0x00500235]
green: base = u8[0x00500236], span = u8[0x00500237]
blue:  base = u8[0x00500238], span = u8[0x00500239]
```

The final per-channel scales are:

```text
red_scale   = u8[0x005000e0]
green_scale = u8[0x005000e1]
blue_scale  = u8[0x005000e2]
```

These scale bytes are exactly the values installed by `display_color_profile_apply` (`0x0001fffc`).

## Outer page factor

`r5` starts at 1. The tail uses:

```text
cmpinco 27, r5, r5
bg       0x00002ca0
```

The compare occurs against the pre-increment value, so generated pages use factors `1..27` inclusive.

For each factor, the routine derives a fixed-point step independently for each channel:

```c
red_step   = factor * red_span   * 28 / 18;
green_step = factor * green_span * 28 / 18;
blue_step  = factor * blue_span  * 28 / 18;
```

All operations are the ROM's unsigned integer `mulo` / `divo` operations.

## Inner 47-sample ramp

Each channel has a 32-bit accumulator initialized to zero at the start of the page. The inner loop starts with `r6 = 47` and terminates through `cmpdeco 1, r6, r6`, therefore it emits 47 calculated triples after the explicit zero triple.

For each sample:

```c
red_acc += red_step;
red = red_base + (red_acc >> 8);
if (red >= 256)
    red = 255;
red = (red_scale * red) >> 7;

/* identical structure for green and blue */
```

The three resulting values are stored as consecutive 16-bit values at offsets `+0`, `+2`, and `+4`.

Important: saturation happens **before** profile scaling. The scale multiplication is not itself clamped by this routine.

A direct structured reconstruction is therefore:

```c
uint8_t base[3] = {
    read8(0x00500234),
    read8(0x00500236),
    read8(0x00500238)
};
uint8_t span[3] = {
    read8(0x00500235),
    read8(0x00500237),
    read8(0x00500239)
};
uint8_t scale[3] = {
    read8(0x005000e0),
    read8(0x005000e1),
    read8(0x005000e2)
};
uint32_t dst = 0x00546008;

memset(dst, 0, 0x120);          /* page 0 */
dst += 0x120;

for (uint32_t factor = 1; factor <= 27; ++factor) {
    uint32_t step[3];
    uint32_t acc[3] = {0, 0, 0};

    for (unsigned c = 0; c < 3; ++c)
        step[c] = factor * span[c] * 28 / 18;

    write16(dst + 0, 0);
    write16(dst + 2, 0);
    write16(dst + 4, 0);
    dst += 6;

    for (unsigned sample = 0; sample < 47; ++sample) {
        for (unsigned c = 0; c < 3; ++c) {
            uint32_t value;
            acc[c] += step[c];
            value = base[c] + (acc[c] >> 8);
            if (value >= 256)
                value = 255;
            value = ((uint32_t)scale[c] * value) >> 7;
            write16(dst + c * 2, (uint16_t)value);
        }
        dst += 6;
    }
}
```

This reconstruction accounts for all bytes written from `0x00546008` through `0x00547f87`.

## Epilogue

After page 27 the routine commits:

```text
0x00546004 = 0
0x00546000 = 1
g1         = 0
ret
```

The caller can therefore interpret `0x00546000` as the ready/valid flag and `0x00546004` as the page/upload index or busy state, but those names remain provisional until their downstream consumers are fully recovered.

## Exact architectural instruction accounting

Ignoring saturation-only instructions, the complete procedure executes a base of **42,908 instructions**, including its final `ret`.

Every channel sample whose unscaled candidate is `>= 256` executes one additional `subo 1, 0, g1` instruction after the failed `cmpobl` fast path. Consequently:

```text
instructions = 42,908 + saturation_count
```

where `saturation_count` is computed naturally while generating the same 27 x 47 x 3 samples. This means the recovered implementation does not need a snapshot-specific hard-coded instruction delta.

The procedure contains no nested calls.

## Recovery consequence

`selector3_apply_mode3_profile()` currently writes only:

```text
0x00546000 = 1
0x00546004 = 0
```

for this part of the corridor. That is not sufficient to represent `0x00002c38` faithfully. The generated `0x1f80` bytes are observable architectural state and are subsequently consumed by the palette-upload path beginning at `0x00002de4`.

The next executable recovery step should therefore implement this exact algorithm as a standalone bridge procedure at `0x00002c38`, with dynamic `42,908 + saturation_count` accounting. `display_color_profile_apply` can then call that recovered procedure compositionally instead of synthesizing its ready/busy endpoint.

# Selector 3 profile application corridor (v0.0.26)

The selector-3 post-frame bridge currently collapses a large observed transition into a single synthetic state application. ROM reconstruction now identifies the concrete profile-application function and three internal helpers responsible for a substantial part of that state.

## Shared entry: `0x0001fcc0`

`0x0001fcc0` is a real callable procedure, not a selector-3-only synthetic block. A complete scan of the reconstructed VF2 2.1 `maincpu` image finds eleven direct call sites:

```text
0x000099fc
0x0000b36c
0x0000b894
0x0000bfe4
0x0000cfa0
0x0001052c
0x00020054
0x00045e1c
0x00053a70
0x000563e4
0x000576d8
```

The routine begins by selecting the active display/profile mode from player state and runtime flags. The observed selector-3 path reaches the profile-table logic with a table stride of `0x100` rooted at `0x0006ee00`.

The relevant concrete corridor is:

```text
0x0001fdd0  call 0x0001ff0c
0x0001fde4  ldob 0x00500064, r12
0x0001fdec  shlo 8, r12, r4
0x0001fdf0  ldob 0x0006eeae(r4), r15
...
0x0001fe20  ldob 0x0006eeae(r4), r5
0x0001fe28  stob r5, 0x00500170
0x0001fe30  ld   0x0006eea4(r4), r5
0x0001fe38  ldos 0x0006eea8(r4), r6
0x0001fe40  ldos 0x0006eeaa(r4), r7
0x0001fe48  st   r5, 0x00501098
0x0001fe50  stos r6, 0x00501020
0x0001fe58  stos r7, 0x00501022
```

This directly explains several writes that were previously represented only as post-state values in `texture_bridge_condition.c`.

## `0x0001fee4` — `display_profile_unit_fill`

This helper is a self-contained counted fill:

```text
0x0001fee4  mov  26, r5
0x0001fee8  lda  0x0050a0e0, r6
0x0001fef0  lda  0x3f800000, r7
0x0001fef8  st   r7, (r6)
0x0001fefc  addo 4, r6, r6
0x0001ff00  cmpdeco 1, r5, r5
0x0001ff04  bl   0x0001fef8
0x0001ff08  ret
```

Semantics:

```c
for (i = 0; i < 26; ++i) {
    write_u32(0x0050a0e0 + i * 4, 0x3f800000);
}
```

The bridge's existing loop that writes twenty-six `1.0f` values is therefore ROM-backed exactly and should eventually be routed through this recovered helper rather than treated as anonymous synthetic state.

## `0x0001ff0c` — `display_profile_mode_constants`

This function first calls `0x0001fee4`, then inspects byte `0x00500064`:

```text
0x0001ff0c  call 0x0001fee4
0x0001ff10  ldob 0x00500064, r15
0x0001ff18  cmpobe 10, r15, 0x0001ff24
0x0001ff1c  cmpobe 6,  r15, 0x0001ff48
0x0001ff20  ret
```

Mode `10` writes two tuning values:

```text
0x0050a124 = 0x3f0f5c29
0x0050a128 = 0x3ef0a3d7
```

Mode `6` writes the larger tuning set:

```text
0x0050a0e4 = 0x3f0a3d71
0x0050a0e8 = 0x3f0a3d71
0x0050a0f0 = 0x3f6b851f
0x0050a0f8 = 0x3f5eb852

0x0050a118 = 0x3f0a3d71
0x0050a11c = 0x3f0a3d71

0x0050a128 = 0x3f28f5c3

0x0050a134 = 0x3f028f5c
```

Other mode values return after the unit fill.

## `0x0001fffc` — `display_color_profile_apply`

This helper resolves the active profile table and explains the three color-scale bytes currently copied by the selector-3 bridge.

```text
0x0001fffc  ldob 0x00500064, r12
0x00020004  ld   0x00500068, r15
0x0002000c  bbc  21, r15, 0x00020018
0x00020010  lda  3, r12
0x00020018  shlo 8, r12, r4
0x0002001c  ldob 0x0006eeb8(r4), r5
0x00020024  ldob 0x0006eeb9(r4), r6
0x0002002c  ldob 0x0006eeba(r4), r7
0x00020034  stob r5, 0x005000e0
0x0002003c  stob r6, 0x005000e1
0x00020044  stob r7, 0x005000e2
0x0002004c  call 0x00002c38
0x00020050  ret
```

The important correction to the previous high-level understanding is that the table is not intrinsically fixed to mode `3`. The normal selector comes from `0x00500064`; runtime flag bit 21 at `0x00500068` forces profile `3`. The current selector-3 bridge happens to materialize the mode-3 result because that is the observed path being matched.

## `0x0004b410` — concrete command submit

The previously identified command leaf is now connected directly to the profile routine:

```text
0x0004b410  mov  1, r3
0x0004b414  st   r3, 0x00550000
0x0004b41c  lda  0x005502e0, r3
0x0004b424  mov  3, r15
0x0004b428  st   r15, (r3)
0x0004b430  st   g0, 4(r3)
0x0004b438  st   g1, 8(r3)
0x0004b440  st   g2, 12(r3)
0x0004b448  ret
```

Thus the observed selector-3 tuple at `0x005502e0..0x005502ec` is an actual command packet generated by firmware code, not an inferred convenience representation.

## `0x00002c38` — color table rebuild

`display_color_profile_apply` immediately calls `0x00002c38`. The function clears the table beginning at `0x00546008`, derives three scaled channel sequences from bytes at `0x00500234..0x00500239`, multiplies each generated channel value by the profile scales at `0x005000e0..0x005000e2`, and stores 16-bit channel triples. Its epilogue is concrete:

```text
0x00002dc4  mov  0, r15
0x00002dc8  st   r15, 0x00546004
0x00002dd0  mov  1, r15
0x00002dd4  st   r15, 0x00546000
0x00002ddc  mov  0, g1
0x00002de0  ret
```

This proves the bridge writes `0x00546004 = 0` and `0x00546000 = 1` are the endpoint of a real color-table reconstruction procedure. Replacing only those two flags with a native helper would be incomplete; the generated table at `0x00546008` is part of the architectural side effect.

## Recovery consequence

The selector-3 bridge still accounts a single synthetic delta of `123638` instructions and `15` calls/returns. This ROM pass does **not** change those totals yet; doing so before differential validation would double-count or under-count work.

What changed is the recovery boundary. The next implementation should peel the synthetic block in this order:

1. recover `0x0001fee4` exactly;
2. recover `0x0001ff0c` exactly;
3. recover `0x0001fffc` together with a faithful `0x00002c38` table rebuild;
4. recover `0x0004b410` as the command leaf;
5. compose those inside `0x0001fcc0` and differentially compare CPU registers plus all touched Model 2 memory;
6. only then subtract their architectural instruction/call totals from `VF2_SELECTOR3_INSTRUCTION_DELTA` and the selector-3 call/return deltas.

`0x0002eab8` and the outer-loop semantics around `0x00011704` remain the next unresolved pieces in the same caller.

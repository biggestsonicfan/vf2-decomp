# v0897 — Original VF2.1 i960 frame 342 producer → real vector-15 UART

Date: 2026-10-19. **Actual owner-ROM execution**; no sample ROM,
snapshot, sound trace, proprietary bytes or WAV committed.

## Ground truth: original i960, no synthetic sound commands

Inputs were the locally retained **original VF2.1 ROM set**
(`epr-18385.12` among other verified chips) and a **pre-frame-342**
original i960 checkpoint saved by the opt-in original-bus writer
observer. The game was stepped with actual controller input mask
`0x20` (KICK). This does **not** imply that a fighter hit someone;
that causality requires an independent collision/call-stack oracle.

The original i960 emitted **five genuine 32-bit command-ring writes**
during this frame. A specific observed original-bus writer was:

```text
original instruction PC: 0x00043924
i960 sound-ring slot:    0x00504024
32-bit word:             0x009E0A7F
frame input mask:        0x00000020
queue count beforehand:  0
```

The pre-instruction PC was recorded inside the memory callback of
the original i960 interpreter, not guessed from its post-step IP.
That producer/slot/word triple was already independently replayed
from the pre-event snapshot via `vf2_audio_writer_replay`.

## Measured ORIGINAL vector-15 ISR vs C shadow drain

A new independent program `vf2_audio_isr_replay` opens two clean
sessions from **the very same original checkpoint**. It executes
one original interpreter frame with identical input in each.
It refuses to proceed unless **both** sessions reproduce the
same original producer/slot/word triple. Then it:

1. Runs `vf2_session_service_sound_drain` on the first session,
   issuing the actual original i960 ROM vector-15 ISR repeatedly
   (including the final disarm pass).
2. Runs `vf2_session_pump_audio` on the other session, whose existing
   shadow i960 drainer models the documented `0x43800` routine.
3. Uses **passive bus observers** to record UART data stores at
   `0x01C80000` for each independently executed session.
4. Compares all transmitted UART bytes (original ISR report,
   original observed MMIO stores, shadow observed MMIO stores and
   shadow pump report), post-drain queue count, read cursor and
   write cursor, and demands `VF2_OK` statuses.

A native GCC/Linux executable from the GitHub Actions
`vf2-audio-isr-replay-linux` artifact **12225822021** built on
the preceding committed code was downloaded and run against the
local owner's original ROM and pre-event checkpoint. The process
returned **exit code 0**. Exact observed output:

```text
audio-isr-replay: ROM-free parser/byte test PASS
ORIGINAL_IP=00043924 RING_SLOT=00504024 RING_WORD=009e0a7f GAME_INPUT=00000020 WRITES=5 PRE_COUNT=0
ORIGINAL_ISR status=0 armed=1 ticks=16 bytes=15 popped=5 uart_writes=15 post_count=0 rcur=6 wcur=6
SHADOW_PUMP status=0 drain=0 bytes=15 filed=5 uart_writes=15 post_count=0 rcur=6 wcur=6
ORIGINAL_ISR_UART=9e0a7fcd74f8ca7ef8cb7ff8ad2100
SHADOW_UART=9e0a7fcd74f8ca7ef8cb7ff8ad2100
MATCH original i960 game command -> vector15 UART vs shadow UART bytes=15
```

The **16 original interrupts** comprise 15 actual UART data writes
plus the ROM's last interrupt entry to disarm the sound line.

The matched UART packet stream is:

```text
9E 0A 7F  CD 74 F8  CA 7E F8  CB 7F F8  AD 21 00
```

The **exact 15 raw UART bytes** are all that is concluded about
the external sound link here. In particular, do not assume every
three-byte group is an L3 frame: Cx-class commands have special
two-byte framing and some `F8` bytes are ignored, which must be
checked independently in the original 68000 receiver.

## v0897b — Complete 15-byte original Motorola 68000 L3 stream differential

Following the exact original-i960/vector-15 UART measurement above,
the entire **15-byte** observed stream was fed, **one byte at a
time**, into two independently initialized receivers:

- **Original VF2.1 MC68000 ROM** (`epr-17574.30`) executing the
  recovered L3 entry via the original CPU interpreter.
- Recovered-C L3 receiver `vf2_sound_board_file_uart_byte`.

The native `vf2_m68k_l3_selection_tests` binary came from the GCC
GitHub Actions artifact `vf2-m68k-sound-differential-linux`
**12226930253** for
[CI #2194](https://github.com/celsowm/vf2-decomp/actions/runs/39335000906).
Using the locally held **original** audio ROM and sample banks,
the actual command was:

```sh
vf2_m68k_l3_selection_tests /local/owner/vf2-roms \
    --uart-stream 9e0a7fcd74f8ca7ef8cb7ff8ad2100
```

**Actual exit code 0, actual output:**

```text
MATCH C/68000 original UART stream bytes=15 ring_count=5 write_cursor=0014
```

The test compares complete sound RAM and modeled SCSP state
after **every single byte** against the original 68000, including
the number/location of original hardware-poke writes at the L3
file boundary. This explicitly uses true original packet framing:
`Cx` commands are two bytes long, and redundant `F8` control
bytes must not be reclassified as the third byte of a synthetic
three-byte packet. Five genuine L3 files are observed, matching the
five original i960 sound-ring commands of this frame.

**Evidence chain now reproduced with local owner ROM:**

```text
original i960 writer (IP 00043924; frame 342) — PASS
   | five genuine original sound-ring writes
   v
original i960 vector-15 ISR — PASS (16 services)
   | 15 original MMIO UART bytes
   v
original 68000 L3 receiver — PASS (isolated byte-exact replay)
   | 5 filed sound ring entries; cursor 0x0014
   =
recovered C 68000 L3 receiver — PASS (all 15 byte checkpoints)
```

This is **not** an assertion of simultaneous original dual-CPU
IRQ scheduling. The 68000 portion was run as an isolated byte
replay, not as a time-accurate serial-bus emulation connecting two
live CPUs. No fighter-collision origin, original 68000 L2/L1
timer ordering, D92/CB2 KEYON for these five commands, or
true SCSP DAC/DSP sound output has been established.

## v0898 — Stereo PCM parity after restoring SCSP-visible sample RAM

The frame-342 original owner-ROM five-command differential now covers
the **9E 0A 7F** KEYON command in both the recovered-C dispatcher and
the original Motorola 68000 interpreter. The independently executed
C-vs-original CPU RAM and SCSP **register** parity had passed, but the
4096-frame **stereo PCM comparison failed**. In the diagnostic's first
failing run:

```text
FRAME342_SCSP_PRE ... C_sample_ram=0 S_sample_ram=1 ...
FRAME342_PCM_RIGHT_FIRST_DIFF sample=0 C=320 S=0 C_left=0 S_left=0
```

This was not a pan or mixing bug. The original MC68000 `MOVEM` block
copied the selected sample page to sound RAM at SCSP start `0x010000`;
the C board still had its SCSP *only* attached to the direct sample ROM.
The original interpreter's SCSP was correctly attached to its own
sound RAM. Identical register values were therefore rendering
**different bytes**.

Fix: on the **strictly opt-in verified frame-342 9E dispatch**,
after the legal 512-byte engine copy and the D72 KEYON tail have
succeeded, attach `board->sound_ram` as the SCSP-visible sample RAM
(`vf2_scsp_attach_sample_ram`). The existing sample-ROM attachment
remains available for addresses beyond the 512KB RAM window.
Leave default initialization unchanged to avoid stale internal
self-pointers in callers that copy `vf2_sound_board` structs.

The added regression asserts the C and original SCSP RAM bindings
explicitly, requires both active slot 0, checks full sound-RAM
parity (minus independently tracked stack/epilogue cells), then
renders **4,096 stereo frames in each independently reached state**.
Left **and** right sample buffers must be byte-for-byte identical,
and the output cannot be all silence.

**Actual owner-ROM test, GitHub Actions GCC artifact
`vf2-m68k-sound-differential-linux` ID 12237322374:**

```text
EXIT:0

FRAME342_9E_PARITY RAM_diff_except_epilogue=0 first=80000 SCSP_C=1 SCSP_S=1
FRAME342_SCSP_PRE C_start=010000 S_start=010000 C_sample_ram=1 S_sample_ram=1 C_addr=00000000 S_addr=00000000 C_step=00000800 S_step=00000800 C_env=0 S_env=0 C_state=0 S_state=0 C_backward=0 S_backward=0
FRAME342_9E_PCM status_c=0 status_s=0 matched_stereo_samples=1 nonzero_frames=920/4096 peak=22568 model_only=1
```

The same original-ROM fixture also reported full non-epilogue RAM
parity for `CD 74`, `CA 7E`, and `CB 7F`; `AD 21 00`
remains refused at `0x1e98` in the C dispatcher as an openly
unrecovered branch.

**Important limits:** `matched_stereo_samples=1` is the diagnostic's
boolean flag meaning **both 4096-frame stereo buffers matched**, not
a count of one sample. This is software-SCSP-model equality, not a
real Model 2 arcade SCSP DSP or DAC comparison. The tested sound
command was genuinely produced by original i960 gameplay code on
the observed controller-input trajectory, but fighter collision
causality and real asynchronous i960/68000 timing remain unproven.
The isolated dispatch fixture initializes an owner-ROM sound board;
it is not a full concurrent snapshot of all historical 68000 state.
No proprietary ROM, sample or captured snapshot is checked into Git.
